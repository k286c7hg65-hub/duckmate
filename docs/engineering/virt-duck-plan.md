## 一、第一性拆解：虚拟鸭子为什么存在？

### 公理链（拆到不可再拆）

**A1. 物理世界实验成本高，虚拟世界成本≈0。**
- 真机：$399 预售、圣诞才发货、一次摔倒可能损坏 14 个 XL330 舵机之一（€45.76/个）
- 虚拟：MuJoCo 仿真，摔一万次零成本，秒级重置
- ⟹ **行为软件必须在虚拟里成熟，真机只做最终验收**——这是虚拟鸭子的存在理由

**A2. 真机硬件是给定的（pollen-robotics Microduck），虚拟环境的 fidelity 有官方保障。**
- 官方 sim = MuJoCo（与我们同源），策略训练于 MuJoCo、导出 ONNX 部署真机
- ⟹ 虚拟里跑通的策略/行为，理论上可直接移植真机（sim2real 是官方设计路径，非我们自创）
- 我们补的是官方没给的：**行为编排层（软件栈）**

**A3. 鸭子本体无「大脑」，行为由外部软件栈决定。**
- 官方给的是 9 个 ONNX 肌肉记忆（50Hz 关节命令）+ 无自主决策
- ⟹ 虚拟鸭子的真正产出 = **可移植行为栈**（认知层+技能库+编排器+视觉闭环），仿真只是孵化器

**A4. RL 训练需要 GPU，且官方训练栈 mjlab 需 CUDA。**
- Macmini M4 16G 已验证只能 debug（CPU 路径，PR #24）
- ⟹ 训练出口 = HF Jobs T4（$0.5/h），这是自训技能的唯一现实路径

### 推论（从公理推出规划结构）

**推论 1：虚拟鸭子不是「仿真鸭子」，是「行为栈孵化器」。**
验收标准 = 行为栈在虚拟里跑通 + 能迁到真机，不是仿真做得多逼真。

**推论 2：三轨（软件/训练/硬件）的本质优先级由 A1 决定：**
- 软件轨（认知+编排）→ 最高优先，虚拟内无限迭代，圣诞前必须成熟
- 训练轨（自训技能）→ 次高，GPU 出口已定，现在就该跑（kick 重训在途）
- 硬件轨（真机）→ 圣诞到货前能做的只有 sim2real 准备清单（校准数据、资产核对）

**推论 3：圣诞是锚点，一切里程碑反推。**
真机 12/25 前到 → 留给 sim2real 移植的时间窗口只有到货后几周
→ 虚拟行为栈必须在到货**前**冻结到「可移植状态」

## 三、规划主线：行为栈孵化 → sim2real 移植

### 里程碑（圣诞反推）

```
M0 (2026-09-02 ✅)  行为栈基础可用
                    = 9策略全通 + 编排 + 技能 + LLM规划 + 视觉
M1 (2026-10 目标)  行为栈「可移植冻结」
                    = 自训踢技能(宽窗) + 长程任务闭环(多轮) + 轨迹日志分析
M2 (2026-12 圣诞)  真机到手 → sim2real 首移
                    = walk/greet/kick 三技能真机验证 + 校准差距回填虚拟
M3 (2027 Q1)       闭环学习雏形
                    = 真机采集轨迹 → 虚拟重训 → 策略更新部署（EmbodiedSkills 全环）
```

### 三轨并行细则

#### 轨 A：软件轨（虚拟行为栈）— 最高优先，圣诞前冻结

| 项 | 现状 → 目标 | 验收 |
|---|---|---|
| 多轮会话状态 | 无记忆 → duck_commander 会话上下文 | 连续两指令引用前一状态（「再踢一次那个球」） |
| 轨迹分析 | 日志落盘 ✅ → 失败模式统计 | 从 logs/traj_*.json 自动提取失败原因分布 |
| 行为栈冻结 | 散落 → 版本化打包 | 单命令复现 demo + 行为清单文档 |
| 视觉闭环增强 | 单帧定位 → 连续追踪 | 球移动中追到并踢出 |

#### 轨 B：训练轨（自训技能）— GPU 出口，立刻启动

| 项 | 状态 → 动作 | 验收 |
|---|---|---|
| kick 宽窗重训 | 训练包就绪（f0fae2f）→ HF Jobs 提交 | verify_kick_window 0.05-0.20m ≥80% |
| 长程编排能力 | 无 → 评估是否需要新策略 | 任务需求清单 vs 现有 9 策略覆盖 |
| 训练成本台账 | 无 → 每技能记录 GPU 时数/成本 | kick ≈ $1-2，未来技能预算参照 |

#### 轨 C：硬件轨（真机 sim2real 准备）— 到货前能做的先做

| 项 | 状态 → 动作 | 验收 |
|---|---|---|
| sim2real 差距清单 | 无 → 建表：仿真资产 vs 真机规格逐项核对 | 表格：物理参数/延迟/传感器差异 |
| 真机规格核对 | 部分（README 有 800g/25cm/14×XL330）→ 补全 | 官方 spec 全量对照虚拟模型 |
| 校准数据采集预案 | 无 → 真机到货第一周测试脚本 | 预写 walk/greet 真机验证脚本 |

## 五、反方自检（最致命反驳）

**「虚拟鸭子是自嗨——真机行为栈直接抄官方 demo 就行，何必自己孵？」**
- 回应：官方给的是单策略 demo（一个 ONNX 对应一个动作），不给**行为编排**（多技能组合、失败恢复、长程任务、LLM 指挥）。我们孵化的正是官方没有的层。且 pollens 的编排层在其闭源 roadmap（M8/M9 自主大脑）——我们自己孵 = 不依赖官方 roadmap。
- 致命残留：若官方圣诞前发布完整编排层（M8 policy channel 已在开发），我们的编排层价值被稀释。缓解：我们的编排层已绑定 LLM 指挥+技能 DSL+视觉闭环，比官方「策略热切换」更上层。仍需监控 M8 进度。

**「sim2real 可能大面积失败——虚拟跑通 ≠ 真机能跑」**
- 回应：官方设计路径就是 MuJoCo→ONNX→真机，BAM 执行器模型+域随机化是为此存在。我们的行为栈跑在官方策略之上，策略层 sim2real 风险由官方承担；我们引入的风险只在编排时序（50Hz 对齐、状态机），可控。
- 缓解：M2 用最小三技能验证，失败点集中在到货前就建清单预测。
