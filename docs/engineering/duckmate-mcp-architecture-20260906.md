# DuckMate 控制栈 MCP 化方案（接口清单 + 优先级）

> 2026-09-06 | 触发：头条 Blender+MCP demo 深读 → Sky「按建议执行」
> 原则：抄接口层设计（协议化+解耦），不抄自主叙事（边界在预算、前提在人给目标）
> 基线事实：上层雏形已跑通（duck_planner/duck_vision/duck_commander NL→DSL 虚拟验证）+ RL 栈门槛分析进行中（joystick 101 维 obs 已源码级确认）+ MuJoCo 仿真全栈可用（9 策略+编排+视觉+踢球）+ microduck 固件全开源

---

## 一、为什么 MCP 化（现状问题 → 目标）

**现状**：duck_commander = 「DeepSeek 意图 → 私有 DSL → 执行」——**单模型私有集成**。换模型要重写适配；训练侧门槛验证（brax 冒烟/超参导出/gate 评估）= 群 bot 人肉 SSH 操作。

**目标**：把 DuckMate 能力（动作/感知/训练/状态）暴露为标准 **MCP server**——
1. **换模型不换接口**：任意 MCP 客户端（Claude/DeepSeek/群 bot/Codex）同一套工具接入
2. **接入成本降为按协议实现**：新能力只写工具注册，不写模型适配
3. **训练闭环自动化**：群 bot/Codex 现在人肉做的门槛验证 → 模型可调用的工具
4. **导演-执行分离**：模型产出指令流（导演），RL 策略/动作库/固件执行（剧组）

**边界（不做什么）**：不做「无头全程自主」——保留人工审核点（关键动作/训练启动前需人确认）。

## 二、三层架构

```
┌─ 客户端层 ─────────────────────────────┐
│ 群 bot / Codex / 桌面 App / 未来任意 LLM  │  ← MCP 客户端（统一协议）
└──────────────┬─────────────────────────┘
               │ 工具调用（JSON-RPC）
┌──────────────▼─────────────────────────┐
│ MCP Server 层（DuckMate Control Hub）    │
│ 训练域 │ 动作域 │ 感知域 │ 系统域          │  ← 本方案主体
└──────────────┬─────────────────────────┘
               │ 真实实现
┌──────────────▼─────────────────────────┐
│ 执行层                                   │
│ brax/mjx RL 栈 │ MuJoCo 仿真 │ 固件(131.rs) │ 舵机 XL330
└────────────────────────────────────────┘
```

运行位置：开发期 server 跑 VPS/AutoDL（训练域）；产品期桌面 App 本地 server（控制域）——同一协议两处部署。

## 四、优先级逻辑

| 优先级 | 域 | 为什么这个顺序 |
|---|---|---|
| P0 | 训练域 | **立刻有用户**（群 bot/Codex 正在人肉做）→ MCP 价值最快验证；且零硬件依赖（纯软件栈） |
| P1 | 动作域 | 产品核心卖点（踢球导演）→ 仿真可先行验证（MuJoCo 已通） |
| P2 | 感知域 | 依赖 P1 动作闭环 + 真机摄像头 |
| P3 | 系统域 | 依赖真机硬件就绪 |

## 六、反方与风险

**反方 1：「已有 duck_commander 私有 DSL 跑通了，MCP 化是重写？」**
- 回应：不是重写——DSL 层保留（产品 prompt 用），MCP 化 = 在 DSL 与执行之间加标准协议层。现有 commander 的意图解析逻辑可直接迁移为 server 内工具逻辑。增量成本 ≈ 接口层 ~20%，换来多模型兼容 + 训练侧自动化。
- 残留：若 DuckMate 最终只绑一家模型（如深度定制对话），MCP 价值减半——但训练侧（群 bot/Codex 多 agent 协作）的 MCP 价值独立成立。

**反方 2：「MCP 是 Anthropic 生态标准，DeepSeek/国产模型支持吗？」**
- 回应：MCP 已捐给标准组织（2025-11 后多厂商支持），DeepSeek 等国产模型通过 MCP 客户端/网关接入无碍；且 server 侧实现与模型无关——server 是纯工具暴露，客户端负责理解工具 schema。真风险 = 弱模型工具调用能力差（function calling 不准）——这正是 P0 放训练域的原因：群 bot/Codex 是强工具调用模型，先验证协议价值。

**反方 3：「训练域工具化 = 让 AI 直接操作训练？安全？」**
- 回应：P0 工具全部**只读/预览/冒烟**（跑验证、导配置、看状态），**不暴露「启动长训练/改代码」**——训练启动保留人工审核点（与「边界在预算、前提在人给」一致）。写操作工具（T4 patch 应用）需显式 confirm 参数。
